## ۰. خلاصه در یک صفحه

- **هدف:** ساخت یک موتور معاملاتی «ایجنتیک» که روی صرافی والکس با حساب اعتباری ۵ میلیون تومانی، فقط اسپات، در یک پنجره ۲ روزه، به‌صورت کاملاً الگوریتمی معامله کند و سودش به تومان محقق شود. داوری با جدول ۳۰۰ امتیازی (۹۰ امتیاز درصد سود، بقیه کنترل ضرر، فعال بودن، پایداری، منطق، استفاده واقعی از AI، مدیریت ریسک، تکرارپذیری، بک‌تست و تست سایه).
- **مسیر:** جمع‌آوری ۲۳۶ استراتژی ← فیلتر و امتیازدهی با بارم چالش ← کشف قوانین و هزینه‌های واقعی والکس با API/MCP ← طراحی ۶ «کمبو» که در آن‌ها **LLM تصمیم‌گیرنده است** و کد فقط فرصت پیدا می‌کند و گاردریل می‌گذارد ← ساخت یک موتور مشترک برای بک‌تست، تست سایه و اجرای واقعی ← سه تست هم‌زمان (A, B, C).
- **مهم‌ترین یافته‌ها:**
  1. هزینه رفت‌وبرگشت در بازار تومانی والکس حدود **۰٫۸ تا ۱٪** است (کارمزد ۰٫۲۵–۰٫۳۰٪ هر طرف + اسپرد + لغزش). اسکلپ‌های دقیقه‌ای و کراس‌اوورها بعد از هزینه **هیچ لبه‌ای ندارند**.
  2. نقدشوندگی والکس بسیار کم است: فقط BTC، USDT، PUMP و PEPE در ۵۵–۶۸٪ دقیقه‌ها معامله دارند؛ بیشتر ارزها فقط در ۵–۱۶٪ دقیقه‌ها.
  3. تنها لبه مثبت قابل‌اعتنا: **خرید افت‌های عمیق (M1) روی ارزهای نقد** با نگهداری چندساعته (بازده ناخالص +۱٫۰٪ در ۴ ساعت و +۱٫۴٪ در ۱۲ ساعت)؛ بعد از آن «جاروی نقدینگی» (M4) با لبه کوچک.
  4. **همه ۶ کمبوی قانون‌محور (بدون LLM) در بک‌تست ۳۵ روزه زیان‌ده‌اند** (از −۰٫۷٪ تا −۱۱٫۶٪).
  5. در ارزیابی کارت‌ها (تست B)، مدل GPT-5.6 Sol بسیار گزیده عمل کرد (فقط ۳ تا ۷٪ کارت‌ها را پذیرفت) و در هر ۵ کمبو نتیجه هر کارت را نسبت به baseline بهتر کرد؛ عمدتاً با **رد کردن معاملات بد**. نمونه کوچک است و قطعی نیست.
  6. **تست سایه زنده (۶٫۵ ساعت، ۱۲ حساب):** موتور بدون حتی یک خطای چرخه یا داده کار کرد. حساب‌های بدون LLM در مجموع **۱۳,۲۴۳ تومان زیان** دادند؛ حساب‌های با LLM در مجموع **۳۴۶ تومان سود** (فقط ۲ معامله). در هر ۴ کمبویی که baseline معامله کرد، نسخه LLM بهتر بود. تنها معامله برنده واقعی، انتخاب آزاد LLM در C5 بود (PUMP، ‎+۱٫۸۴٪‎ در ۲۰ دقیقه).
  7. **مشکل اصلی:** LLM آن‌قدر محتاط است که تقریباً معامله نمی‌کند — خوب برای کنترل ضرر، بد برای امتیاز سود و فعالیت. و حدود **۸۰٪ فراخوانی‌های LLM در سایه هدر رفت** چون کارت‌هایی که کد به هر حال رد می‌کرد به مدل فرستاده شدند.
- **وضعیت فعلی:** هر سه تست تمام شده‌اند (۱۹:۰۰). حدود ۷۰۵ هزار از ۱ میلیون توکن مصرف شده (~۲۹۵ هزار باقی). قدم بعد: انتخاب نهایی، رفع دو مشکل بالا، ساخت بروکر واقعی و شروع اجرای واقعی.

## ۳. خط زمانی: مسیری که رفتیم

### روز اول — چهارشنبه ۲۹ مهر ۱۴۰۵ (2026-10-21)
1. **شروع:** دریافت مستندات چالش و درخواست: «۱۰۰+ استراتژی اسکلپ سریع جمع کن، استراتژی‌های مخصوص دارایی‌های غیر والکسی را حذف کن، با معیارهای چالش مرتب کن.» دامنه بعد از پرسش‌وپاسخ به «اسکلپ + استراتژی‌های الگوریتمی کوتاه‌مدت» گسترش یافت (lead-lag، آربیتراژ مثلثی، maker و…).
2. **تحقیق:** ۲۳۶ استراتژی یکتا از freqtrade، TradingView، Hummingbot، مقالات و… ← فیلتر ← ۱۸۷ + ۴ استراتژی تطبیق‌یافته (W1–W4) ← امتیازدهی با بارم ← صفحه رتبه‌بندی تعاملی.
3. **اصلاح شرایط:** پنجره ۲ روزه (نه ۳) تأیید شد.
4. **اتصال به والکس:** نوشتن اسکریپت فقط‌خواندنی `wallex_check.py`، اتصال MCP والکس، بررسی کارمزد واقعی، موجودی، rate limit، قوانین بازار و داده کندل.
5. **ثبت دانسته‌ها:** ساخت `NOTES.md` و راه‌اندازی مخزن GitHub برای ادامه کار روی لپ‌تاپ.

### روز دوم صبح — ۳۰ مهر (2026-10-22)
6. **سایزینگ و کمبوها v1:** درخواست «پوزیشن حدود ۱٪، حداقل ۳ کمبو (پرریسک، کم‌ریسک، مدیریت سرمایه قوی، کمترین افت، انتخاب LLM)، یک ارز با پارامترهای متفاوت در کمبوهای مختلف» ← کشف محدودیت minNotional و پله مقدار ← ۵ کمبو.
7. **کمبوها v2 (تأییدشده):** سه تغییر اساسی به درخواست محسن:
   - LLM باید **نقش تصمیم‌گیرنده واقعی** داشته باشد («آخر این پروژه باید یک ایجنت هوش مصنوعی باشه که معامله کنه»).
   - کد باید **مستقل از مدل** باشد (مدل ممکن است عوض شود).
   - سرمایه تست هر کمبو **۲٫۵ میلیون تومان** («چون تو واقعیت هم میخوام بگم با نصف سرمایه کار کنه»).
   ← ۶ کمبو (C1–C6)، هر کدام با نسخه baseline بدون LLM برای سنجش «ارزش افزوده AI».
8. **پلان تست:** طراحی پلان کامل بک‌تست + تست سایه از نگاه «معامله‌گر حرفه‌ای ۲۰ ساله + متخصص ایجنت هوش مصنوعی»، با **۳ دور بازبینی**، اجرای هم‌زمان همه تست‌ها و متریک‌های هم‌راستا با بارم ← `docs/BACKTEST_PLAN.md`.
9. **فشردگی زمان:** معلوم شد پنجره معاملاتی از صبح امروز شروع شده و باید **امروز** استراتژی نهایی انتخاب و **از امشب** اجرا شود. پلان به زمان‌بندی فشرده تبدیل شد؛ سؤالات مدیریت خطا، تنظیم‌پذیری زمان اجرا و گزارش کامل همه ۱۲ تست هم اضافه شد.
10. **ساخت کد:** داده ۳۵ روزه (۳۰ نماد × ۳۶ روز = ۱۰۸۰ درخواست، ۵۴ ثانیه) ← شبیه‌ساز اجرا + ۱۵ تست طلایی ← ویژگی‌ها و اسکنرها ← موتور و گاردریل‌ها ← بک‌تست baseline.
11. **اولین بک‌تست: همه کمبوها زیان‌ده.** به جای پنهان کردن، رفتیم سراغ شواهد: **مطالعه لبه** (edge study) نشان داد کدام اسکنرها قبل از هزینه لبه دارند ← کمبوها با شواهد بازتنظیم شدند (ارزهای نقد، نگهداری طولانی‌تر، حد ضرر بازتر) ← LLM نقش «انتخاب‌گر» گرفت.
12. **لایه LLM:** ساخت آداپتور مستقل از مدل (OpenAI-compatible، Anthropic، opencode، دستور خط فرمان، mock) + پرامپت‌ها + ارزیابی کارت‌ها + تست سایه + گزارش‌ساز + `run_all.py`.
13. **مدل و پلتفرم:** محسن Ollama نمی‌خواست؛ تلاش برای GPT-6.1 Sol روی opencode به دو مانع خورد (عدم دسترسی به مدل + تداخل پایگاه داده opencode CLI با نسخه دسکتاپ). راه نهایی: **API مستقیم CodeCraft با GPT-5.6 Sol/Luna**. مانع بعدی: Cloudflare درخواست‌های پایتون را با 403 رد می‌کرد ← با آزمایش User-Agent حل شد.
14. **بودجه توکن:** سهمیه کل ۱ میلیون توکن ← شمارنده و سقف توکن مشترک بین فرآیندها ساخته شد. به تصمیم محسن کل سهمیه برای تست‌های امروز استفاده می‌شود.
15. **اجرای تست‌ها:** ساعت **۱۲:۲۶** با یک دستور، سه تست هم‌زمان شروع شد. A در چند ثانیه و B در ۶ دقیقه تمام شد؛ C تا ۱۹:۰۰ ادامه داشت.
16. **پایش حین تست:** ساعت ۱۳:۲۶ گزارش میانی به خاطر خطای encoding ویندوز نیمه‌کاره ماند ← رفع شد. ساعت ۱۵:۳۵ نگرانی «هیچ معامله‌ای بسته نشده» بررسی شد: موتور سالم بود؛ علت، نگهداری طولانی طراحی‌شده و بازار آرام بود (با داده ۳۵ روزه تأیید شد که بازه‌های ۳ ساعته بدون کارت برای C2 و C4 عادی است). به درخواست محسن، **پوزیشن‌های باز و ارزش لحظه‌ای** به گزارش ساعتی اضافه شد.
17. **پایان تست‌ها (۱۹:۰۰):** همه پوزیشن‌های مجازی به تومان بسته شدند و گزارش نهایی ساخته شد. یک باگ در محاسبه بازده نهایی سایه پیدا و رفع شد (بخش ۱۷) و نتایج از روی معاملات بسته‌شده دوباره محاسبه شدند.

## ۸. معماری سیستم

### ۸.۱ اصل «یک موتور، سه حالت»
همان کد اسکنر، تصمیم، گاردریل و مدیریت پوزیشن در **بک‌تست**، **تست سایه** و **اجرای واقعی** اجرا می‌شود؛ فقط منبع داده و «بروکر» عوض می‌شود. این هم اعتبار بک‌تست را بالا می‌برد و هم امتیاز «قابل اجرای مجدد».

### ۸.۲ جریان هر دقیقه
```
کندل ۱ دقیقه جدید
   │
   ├─► features: ساخت کندل‌های ۵/۱۵/۶۰ دقیقه و اندیکاتورها (فقط داده گذشته)
   ├─► regime: رژیم هر ارز (trend_up / range / down / dead) + رژیم BTC از BTCUSDT
   ├─► scanners: کارت‌های فرصت (M1..M8, MOM)
   │
   ├─► برای هر کارت:
   │      فیلترهای سطح کمبو (رژیم، BTC)            ← کد
   │      policy.decide(card, context)              ← Baseline یا LLM
   │      guardrails: کلمپ/رد + محاسبه سایز         ← کد
   │      سفارش در کندل بعد (open t+1)              ← شبیه‌ساز یا بروکر واقعی
   │
   ├─► مدیریت پوزیشن‌ها: SL، TP، BE، trail، زمان، محافظ گیر افتادن
   ├─► ریسک حساب: توقف روزانه، قطع‌کن، مکث بعد از ضرر
   └─► لاگ: هر کارت، هر تصمیم (ورودی/خروجی LLM)، هر رد، هر معامله
```

### ۸.۳ قواعد ثابت
1. **بدون نگاه به آینده:** تصمیم در لحظه t فقط داده تا پایان کندل t را می‌بیند؛ اجرا از کندل t+1. کندل‌های تایم‌فریم بالاتر فقط بعد از بسته شدن کامل استفاده می‌شوند.
2. **شبیه‌سازی بدبینانه:** هرجا ابهام هست، فرض بدتر.
3. **همه چیز لاگ می‌شود** ← همین لاگ‌ها «لاگ دلیل معامله» تحویلی چالش‌اند.
4. **سود فقط به تومان:** پایان هر بازه، همه پوزیشن‌ها با Market بسته می‌شوند.
5. **مستقل از مدل.**
6. **هیچ خطایی نباید هم پوزیشن را بی‌دفاع بگذارد و هم ربات را از کار بیندازد.**

| reflect | C6 | بعد از هر معامله بسته‌شده یک درس قابل استفاده می‌نویسد (حافظه) | `prompts/reflect_v1.md` |
| native | C5 | بدون اسکنر، هر ۱۵ دقیقه از جدول ارزها حداکثر ۲ خرید انتخاب می‌کند | `prompts/native_v1.md` |

خروجی همیشه یک JSON با schema ثابت است:
```json
{"action":"enter|skip","size_tmn":number,"sl_pct":number,
 "tp_plan":[{"pct":number,"portion":number}],"time_stop_min":number,
 "confidence":0..1,"thesis":"<=25 words","invalidation":"<=15 words"}
```
پرامپت تصمیم واقعیت‌های بازار را به مدل می‌گوید (هزینه رفت‌وبرگشت ~۰٫۸–۱٪، شواهد ۳۵ روزه که «خرید افت عمیق روی ارز نقد لبه کوچک دارد و خرید شکست/مومنتوم لبه ندارد»، فقط لانگ، بدون میانگین‌گیری، «رد کردن» پیش‌فرض است).

### ۹.۲ ورودی مدل (کارت)
حدود ۵۰۰ توکن: اسکنر و توضیحش، نمای ارز (۱۲ کندل اخیر در چند تایم‌فریم، RSI، ATR، فاصله از VWAP، درصد دقیقه‌های معامله‌دار)، نمای بازار (رژیم BTC، بازده ۱۵ دقیقه، نرخ تتر)، وضعیت حساب، بازه‌های مجاز. در ارزیابی آفلاین (تست B) **ناشناس‌سازی** می‌شود (اسم ارز ← `ASSET_07`، بدون تاریخ) تا مدل نتواند قیمت‌های گذشته را «به یاد بیاورد».

### ۹.۳ آداپتور مستقل از مدل (`wallex_agent/llm/adapter.py`)
- **Backendها:** `openai_compat` (هر API سازگار با OpenAI)، `anthropic`، `opencode_server`، `command` (هر CLI)، `mock` (آفلاین برای تست خط لوله).
- **پروفایل‌ها** در `config/llm.yaml`؛ عوض کردن مدل = عوض کردن یک اسم در دستور (`--llm sol56`).
  - فعال: `sol56` (gpt-5.6-sol، reasoning کم)، `terra56`، `luna56`، `sol56_medium`.
  - آماده ولی استفاده‌نشده: `sol_opencode`، `sol_opencode_cli`، `sol_api`، `sol_openrouter`، `claude_api`.
- **زنجیره جایگزین برای هر نقش:** decide/risk_manager/orchestrator/native: Sol ← Terra؛ reflect: Luna ← Sol؛ card_eval: Luna. (در دستور هم می‌شود لیست جداشده با کاما داد.)
- **قابلیت‌ها:** ۲ بار تلاش مجدد برای JSON نامعتبر (با گفتن خطا به مدل)، اعتبارسنجی schema، کش فایلی (هر کلید یک فایل)، محدودکننده نرخ (۳۰۰ فراخوانی در ساعت، ۴ هم‌زمان)، امتحان چند شکل بدنه درخواست در خطای 400/422.
- **شمارنده توکن (TokenLedger):** هر فراخوانی در `.cache/token_ledger.txt` ثبت می‌شود (مشترک بین فرآیندها). دو سقف: کل حساب (`token_budget_total: 900000` چون ~۶۵ هزار قبلاً خرج شده بود) و سقف هر اجرا (متغیر `LLM_TOKEN_CAP`). وقتی سقف پر شود فراخوانی انجام نمی‌شود و تصمیم «خطا» ثبت می‌شود ← ورود جدید انجام نمی‌شود ولی پوزیشن‌های باز با SL/TP/زمان کد مدیریت و بسته می‌شوند.
- **Cloudflare:** درگاه CodeCraft پشت Cloudflare است و درخواست‌های پایتون با User-Agent پیش‌فرض (و حتی Node) را با 403 رد می‌کرد. آزمایش (`tools/ua_probe.py`) نشان داد UA `opencode/1.19.3` قبول می‌شود ← پیش‌فرض کد شد (قابل تغییر با `LLM_USER_AGENT`).

### ۹.۴ مصرف توکن اندازه‌گیری‌شده
- تست کوتاه `llm_check`: Sol ۱۰۵۷–۱۵۷۸ توکن، Luna ~۱۱۰۰ توکن در هر فراخوانی؛ تأخیر Sol ۸–۱۳ ثانیه، Luna ۶–۸ ثانیه.
- تصمیم واقعی روی کارت (تست B): **میانگین ~۲,۴۰۰ توکن** (شامل توکن‌های استدلال).
- تست سایه: ۱۰۱ فراخوانی، ۲۷۳ هزار توکن، **میانگین ~۲,۷۰۰** (فراخوانی‌های C5 و ارکستراتور C6 جدول چند ارز را می‌گیرند و بزرگ‌ترند). تأخیر میانگین ~۹ ثانیه، بیشترین ۲۲ ثانیه.
- یعنی با ۱ میلیون توکن کلاً ~۴۰۰ تصمیم ممکن است.
- **مصرف کل تا پایان تست‌ها:** شمارنده سیستم ۶۴۷,۷۳۵ توکن در ۲۵۴ فراخوانی (B حدود ۳۵۰ هزار، سایه ۲۷۳ هزار، چک‌ها بقیه) + ~۵۷ هزار پیش از ساخت شمارنده ≈ **۷۰۵ هزار** (پنل CodeCraft ساعت ۱۵:۳۵ عدد ۵۵۲,۵۷۰ را نشان داد که با شمارنده هم‌خوان بود). **باقی‌مانده ≈ ۲۹۵ هزار توکن.**

## ۱۰. شبیه‌ساز اجرا (`wallex_agent/sim/fill_model.py`)

مهم‌ترین قسمت برای اعتبار بک‌تست. همه قواعد بدبینانه‌اند:

| موضوع | قاعده |
|---|---|
| زمان اجرا | سیگنال روی بسته شدن کندل t؛ سفارش در open کندل t+1. اگر LLM بیش از ۴۵ ثانیه طول بکشد، یک کندل دیرتر |
| Market | خرید: `open × (1 + اسپرد×۱٫۵/۲ + ۰٫۰۵٪ لغزش + جریمه کهنگی)`؛ فروش برعکس |
| جریمه کهنگی | ۰٫۰۲٪ به ازای هر دقیقه که ارز معامله نداشته، حداکثر ۰٫۵٪ |
| اسپرد | از snapshot اسپرد هر بازار (`research/combos/market_rules_snapshot.csv`) × ۱٫۵؛ در تست سایه اسپرد زنده جایگزین می‌شود |
| Limit / حد سود | فقط اگر **یک معامله واقعی** از قیمت عبور کند (لمس کافی نیست) |
| Stop | فقط با معامله واقعی؛ قیمت fill = `min(stop, open)` ← گپ پایین‌تر از استاپ لحاظ می‌شود |
| SL و TP در یک کندل | **همیشه SL** |
| کارمزد | Maker ۰٫۲۵٪، Taker ۰٫۳۰٪ |
| حداقل سفارش | ۵۰,۰۰۰ تومان روی خرید **و فروش**؛ گرد کردن مقدار به پله بازار |
| محافظ گیر افتادن | ارزش پوزیشن ≤ ۵۲,۰۰۰ ← فروش فوری |
| کندل بدون معامله | هیچ fill |

**۱۵ تست طلایی** (`tests/test_fill_model.py`) با جواب دستی‌حساب‌شده (گپ زیر استاپ، SL و TP هم‌زمان، Limit لمس‌شده، حجم صفر، minNotional روی فروش بعد از ضرر، پله درشت و…). `run_all.py` اگر یکی رد شود اجرا را شروع نمی‌کند. همه سبزند.

## ۱۱. اسکنرها و تشخیص رژیم (`wallex_agent/scanners.py`)

| کد | نام | تایم‌فریم | شرط (خلاصه) |
|---|---|---|---|
| M1 | Bollinger dip | ۵ دقیقه | بسته شدن ۰٫۵٪ زیر باند پایین بولینگر + RSI زیر ۳۰ + زیر EMA50 |
| M2 | VWAP reclaim | ۵ دقیقه | کندل قبل زیر VWAP روزانه − ۲ انحراف معیار، کندل فعلی بالای سقف کندل قبل و سبز |
| M3 | Volatility breakout (لری ویلیامز) | ۵ دقیقه | عبور از open جلسه ۴ساعته + ۰٫۵ × دامنه جلسه قبل، بالای EMA200، حجم ۱٫۵ برابر |
| M4 | Liquidity sweep | ۱۵ دقیقه | کف کندل زیر کف ۱۰ کندل قبل ولی بسته شدن بالای آن + z-score حجم > ۱٫۵ |
| M5 | Trend pullback | ۵ دقیقه | روند ۱ ساعته صعودی، بالای EMA200، EMA8 > EMA21، RSI اخیر زیر ۴۱، کراس MACD |
| M6 | Squeeze breakout | ۱۵ دقیقه | خروج بولینگر از کانال کلتنر بعد از ۶ کندل فشرده + مومنتوم مثبت + حجم |
| M7 | Volume spike reversal | ۵ دقیقه | z-score حجم ≥ ۳، بسته شدن در یک‌سوم بالای کندل، کف ۱۲ کندل |
| M8 | Relative strength | ۱۵ دقیقه | ۳ ارز قوی‌تر از BTC که به EMA21 برگشته‌اند |
| MOM | Momentum rotation | ۴ ساعت | ۲ ارز با بیشترین مومنتوم (baseline کمبو C5) |

**رژیم:** هر ارز روی ۱۵ دقیقه یکی از `trend_up / range / down / dead` (dead = نقدشوندگی خیلی کم). رژیم بازار از **BTCUSDT** خوانده می‌شود، نه BTCTMN؛ چون قیمت هر جفت تومانی = قیمت دلاری × نرخ تتر، و حرکت تتر نباید «روند کریپتو» دیده شود.

## ۱۲. گاردریل‌ها و مدیریت ریسک (`wallex_agent/engine.py`)

ترتیب بررسی هر تصمیم «ورود» (اگر یکی رد شود، کارت با دلیلش لاگ می‌شود):

1. ارز در لیست مجاز کمبو باشد.
2. نقدشوندگی ۱۵ دقیقه اخیر ≥ حداقل کمبو.
3. در همان ارز پوزیشن باز نباشد (یک پوزیشن در هر ارز).
4. توقف روزانه فعال نشده باشد؛ مکث یا قطع‌کن فعال نباشد؛ کول‌داون ارز بعد از استاپ تمام شده باشد.
5. سقف تعداد ورود در ساعت.
6. سقف تعداد پوزیشن هم‌زمان؛ سقف هر خوشه (میم/ماژور/سایر).
7. SL داخل بازه کمبو کلمپ شود.
8. سایز: یا از تصمیم (کلمپ در بازه)، یا در C3 از ریسک ثابت ÷ فاصله استاپ (و نصف شدن ریسک زیر ۹۸٪ قله).
9. سقف درگیری کل؛ **حداقل ۵۰٪ نقد**؛ سقف گرمای کل (C3).
10. حد سودها داخل بازه کمبو.

**مدیریت پوزیشن:** حد ضرر همیشه (K1 = ۱۰۰٪)، حد سود یک یا دو مرحله‌ای، بعد از TP1 استاپ به نقطه سر به سر (entry × ۱٫۰۰۶)، BE trigger، trailing بر اساس ATR، خروج زمانی، محافظ گیر افتادن.

**در اجرای واقعی (طراحی‌شده، هنوز ساخته نشده):** همه حد ضررها به‌صورت سفارش stop **روی خود والکس** ثبت می‌شوند تا اگر برنامه کامل از کار افتاد، استاپ‌ها سر جایشان باشند؛ هر سفارش `client_id` یکتا برای جلوگیری از سفارش تکراری؛ آشتی (reconcile) دوره‌ای با موجودی والکس؛ بستن همه به تومان قبل از پایان.

## ۱۳. طراحی تست‌ها

### ۱۳.۱ چرا سه تست؟
- بک‌تست کامل با LLM روی ۳۵ روز **خیلی گران** است (ده‌ها هزار کارت × ۲,۴۰۰ توکن) و **خطر یادآوری قیمت** دارد.
- تست سایه زنده معتبرترین است، اما فقط چند ساعت داده می‌دهد (نمونه کم).
- پس سه تست مکمل، هم‌زمان:

| تست | چه می‌سنجد | داده | LLM |
|---|---|---|---|
| **A — بک‌تست baseline** | آیا قواعد کمبوها بدون AI سودده‌اند؟ کدام بازه‌ها معقول‌اند؟ | ۳۵ روز کندل ۱ دقیقه | ندارد |
| **B — ارزیابی کارت‌ها** | ارزش افزوده AI روی هر تصمیم: همان کارت با پارامتر baseline و با تصمیم LLM شبیه‌سازی می‌شود | کارت‌های ۱۲ روز آخر، ناشناس‌شده | دارد |
| **C — تست سایه زنده** | همه ۱۲ حساب (۶ کمبو × با/بدون LLM) روی بازار زنده، با سفارش مجازی | زنده | دارد |

### ۱۳.۲ جزئیات تست B (مهم‌ترین شاهد «استفاده واقعی از AI»)
- برای کمبوهای C1، C2، C3، C4، C6: نمونه تصادفی (seed ثابت ۴۲) از کارت‌های واجد شرایط ۱۲ روز آخر؛ **۳۰ کارت در هر کمبو** (به خاطر بودجه توکن).
- برای هر کارت: `outcome_baseline` و `outcome_llm` با همان شبیه‌ساز (افق ۴۸ ساعت).
- **کنترل منفی (shuffle):** تصمیم‌های LLM بین کارت‌ها به‌هم‌ریخته می‌شود (همان نرخ ورود، ولی روی کارت‌های تصادفی). اگر نتیجه واقعی بهتر از به‌هم‌ریخته نباشد، LLM فقط «کم‌تر معامله کردن» را یاد گرفته، نه «انتخاب درست» را.
- **فاصله اطمینان bootstrap ۹۵٪** برای lift.
- **دقت فیلتر:** از کارت‌های ردشده چند درصد واقعاً ضررده بودند و از پذیرفته‌ها چند درصد سودده.
- **کالیبراسیون:** Brier score بین `confidence` و نتیجه.

### ۱۳.۳ جزئیات تست C
- `LiveFeed`: هر چرخه آخرین کندل‌های ۱ دقیقه ۳۰ نماد از `/v1/udf/history` + اسپرد زنده از `/v1/markets`. چرخه ~۳ ثانیه.
- ۱۲ حساب، هر کدام ۲٫۵ میلیون؛ C5-LLM هر ۱۵ دقیقه، ارکستراتور C6 هر ۳۰ دقیقه، بازتاب C6 بعد از هر معامله بسته‌شده.
- `heartbeat.json` وضعیت هر حساب را هر چرخه می‌نویسد؛ `run_all` در صورت کرش تا ۵ بار ری‌استارت می‌کند.

### ۱۳.۴ یک دستور برای همه
`run_all.py`:
1. **Preflight:** ۱۵ تست طلایی ← به‌روزرسانی داده ← `llm_check` برای هر پروفایل. اگر یکی رد شود، اجرا شروع نمی‌شود.
2. اجرای هم‌زمان A، B (یک فرآیند برای هر مدل) و C به‌صورت فرآیندهای جدا با لاگ جدا؛ سقف توکن جدا برای هر فرآیند (C: ۴۵۰ هزار، B: ۳۵۰ هزار).
3. گزارش میانی هر ۶۰ دقیقه و گزارش نهایی در ساعت `--until`.

### ۱۳.۵ سه دور بازبینی پلان (خلاصه)
- **نگاه معامله‌گر:** رژیم از BTCUSDT نه BTCTMN؛ اسپرد بدبینانه؛ ممنوعیت fill روی کندل بی‌معامله؛ معیار پنجره‌های ۲ روزه غلتان (چون مسابقه ۲ روزه است)؛ minNotional روی فروش؛ افت هم از قله (D1) هم از سرمایه اولیه (D2).
- **نگاه متخصص ایجنت:** شبیه‌سازی تأخیر LLM؛ روش کارت به جای بک‌تست کامل LLM؛ ناشناس‌سازی + کنترل منفی؛ متریک ثبات تصمیم؛ متریک‌های اثبات «AI واقعی».
- **نگاه مهندسی:** اجرا روی ویندوز (شبکه)؛ گارد `__main__` برای multiprocessing ویندوز؛ یک DataFeed مشترک برای rate limit؛ تکرارپذیری؛ تست‌های طلایی.

### ۱۳.۶ پلان در برابر آنچه واقعاً اجرا شد (صادقانه)
| در پلان | در عمل | دلیل |
|---|---|---|
| Walk-forward با ۳ fold + شبکه ۶۴ کانفیگ + holdout | یک کانفیگ پایه برای هر کمبو روی کل ۳۵ روز + همه پنجره‌های ۲ روزه غلتان + چند sweep شواهدمحور جدا (`tools/`) | زمان؛ و baselineها با هر تنظیمی منفی ماندند، پس شبکه بزرگ ارزشی نداشت |
| ۲۵۰ کارت در هر کمبو و مقایسه ۲–۳ مدل در B | ۳۰ کارت در هر کمبو، فقط Sol | سهمیه ۱ میلیون توکن |
| تست سایه با دفتر سفارش واقعی (walk the book) و ضبط‌کننده | سایه با کندل زنده + اسپرد زنده و همان شبیه‌ساز بک‌تست | زمان |
| ذخیره وضعیت سایه در SQLite و ادامه بعد از ری‌استارت | ری‌استارت خودکار، ولی حساب‌ها از صفر شروع می‌شوند | زمان (در لیست کارها) |
| فیلتر ML برای C4 | جانشین قانونی (RSI پانزده‌دقیقه‌ای < ۴۵) | زمان |
| مدل GPT-6.1 Sol روی opencode | GPT-5.6 Sol با API مستقیم CodeCraft | عدم دسترسی + مشکل opencode CLI |

**هشدار روش‌شناختی:** بازه‌های کمبوها با مطالعه لبه روی **کل ۳۵ روز** بازتنظیم شدند و کارت‌های تست B از ۱۲ روز آخر همان بازه‌اند. پس baseline در B کاملاً «خارج از نمونه» نیست. ولی چون همان کارت‌ها به هر دو سیاست داده می‌شوند، مقایسه LLM با baseline منصفانه است؛ فقط سطح مطلق نتایج ممکن است خوش‌بینانه باشد.

**مقایسه جفتی (AI lift در سایه = بازده با LLM − بازده بدون LLM):** C1 ‎+۰٫۱۳‎ واحد درصد · C3 ‎+۰٫۰۸‎ · C5 ‎+۰٫۲۷‎ · C6 ‎+۰٫۰۷‎ · C2 و C4 صفر (هیچ‌کدام معامله نکردند). **در ۴ از ۴ کمبویی که baseline معامله کرد، نسخه LLM بهتر بود.**

**قیف کارت‌ها (چرا معامله‌ها کم بود):**
- بازار امروز برای بیشتر ارزها در رژیم «نزولی» یا «مرده» بود؛ فیلتر رژیم C2، C4 و C6 بیشتر کارت‌ها را قبل از تصمیم کنار گذاشت (C6: ۹ کارت «مرده»، ۷–۱۰ «نزولی»).

### راه‌اندازی یک‌باره
1. پایتون Anaconda (numpy، pandas و pyyaml همراهش هست).
2. در پوشه `wallex-bot`، فایل `.env` بسازید (از روی `.env.example`):

3. رفتن به پوشه:
   ```
   cd C:\Users\rajman\Documents\wallex-bot
   ```

### دستورها
| کار | دستور |
|---|---|
| چک API والکس (فقط خواندنی) | `python wallex_check.py` |
| دریافت/به‌روزرسانی داده | `python -m wallex_agent.data.fetch --days 35` |
| تست‌های طلایی شبیه‌ساز | `python tests/test_fill_model.py` |
| چک آمادگی مدل | `python tools/llm_check.py --llm sol56` (یا `luna56`) |
| **همه تست‌ها با هم** | `python run_all.py --llm sol56 --cards-llm sol56 --until 19:00` |
| فقط بک‌تست | `python -m wallex_agent.backtest --days 35` |
| فقط ارزیابی کارت | `python -m wallex_agent.eval_cards --llm sol56 --anonymize --per-combo 30` |
| فقط سایه | `python -m wallex_agent.shadow --llm sol56 --until 19:00` |
| ساخت گزارش دستی | `python -m wallex_agent.report --out runs\<id>\report --bt runs\<id>\backtest --cards runs\<id>\cards_sol56 --shadow runs\<id>\shadow` |

### گزینه‌های `run_all.py`
| گزینه | پیش‌فرض | معنی |
|---|---|---|
| `--llm` | (الزامی) | پروفایل مدل برای سایه |
| `--cards-llm` | همان `--llm` | پروفایل(های) تست B؛ لیست با کاما = مقایسه مدل‌ها |
| `--until` | (الزامی) | ساعت پایان به وقت تهران |
| `--days` | ۳۵ | روزهای داده بک‌تست |
| `--cards-per-combo` | ۳۰ | تعداد کارت تست B در هر کمبو |
| `--cap-shadow` / `--cap-cards` | ۴۵۰,۰۰۰ / ۳۵۰,۰۰۰ | سقف توکن هر فرآیند |
| `--report-every` | ۶۰ | دقیقه بین گزارش‌های میانی |
| `--skip` | — | مثلاً `A,B` برای رد کردن تست‌ها |

**عوض کردن مدل:** فقط اسم پروفایل در `--llm` عوض شود (مثلاً `terra56`). برای مدل یا درگاه جدید، یک پروفایل در `config/llm.yaml` اضافه و کلیدش در `.env` گذاشته شود.

## ۲۱. واژه‌نامه

| اصطلاح | معنی |
|---|---|
| کمبو (Combo) | یک «شخصیت معاملاتی» کامل: اسکنرها + ارزها + بازه‌های مجاز + قواعد ریسک + نقش LLM |
| کارت فرصت (Card) | خروجی اسکنر: یک موقعیت احتمالی در یک ارز در یک لحظه، با استاپ و هدف پیشنهادی |
| Baseline | نسخه بدون LLM هر کمبو با قواعد ثابت؛ برای سنجش ارزش افزوده AI |
| Policy | بخشی که روی کارت تصمیم می‌گیرد (Baseline یا LLM) |
| گاردریل | قواعد کد که تصمیم را کلمپ یا رد می‌کنند؛ برای هر دو سیاست یکسان |
| AI lift | اختلاف نتیجه با LLM و بدون LLM |
| کنترل منفی (shuffle) | به‌هم‌ریختن تصمیم‌های LLM بین کارت‌ها برای اینکه ببینیم انتخاب واقعاً هوشمند است یا فقط «کم‌تر معامله کردن» |
| ناشناس‌سازی | حذف اسم ارز و تاریخ از ورودی LLM در تست‌های تاریخی |
| تست سایه (Shadow) | اجرای زنده روی بازار واقعی با سفارش مجازی |
| minNotional | حداقل ارزش هر سفارش (۵۰ هزار تومان) |
| stepSize | پله مقدار قابل سفارش |
| SL / TP / BE | حد ضرر / حد سود / انتقال استاپ به نقطه سر به سر |
| PF | Profit Factor = مجموع سودها ÷ مجموع زیان‌ها |
| R | واحد ریسک = فاصله ورود تا استاپ |
| JSP | Judge Score Proxy — امتیاز تقریبی داور از ۳۰۰ برای رتبه‌بندی داخلی |
| رژیم | وضعیت بازار ارز: صعودی، رنج، نزولی، مرده |
| محافظ گیر افتادن (Stuck guard) | فروش فوری وقتی ارزش پوزیشن نزدیک حداقل سفارش می‌شود |
| TokenLedger | شمارنده و سقف مصرف توکن مدل |
| Preflight | چک‌های قبل از اجرا (تست طلایی، داده، مدل) |
